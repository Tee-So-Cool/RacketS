# ทดลองยกระดับการค้นคว้าสเปกไม้แบด 15 รุ่น

ให้แต่ละสเปกที่เผยแพร่มีหลักฐานที่คนอื่นเปิดตรวจซ้ำได้ เริ่มจากรหัสรุ่น เวต เพดานเอ็น และปีเปิดตัวของไม้ใหม่สามแบรนด์ที่เน้นในไทย

ชุดข้อมูลตั้งต้นมี 53 รายการของ Yonex, Victor และ Li-Ning ที่แสดงปี 2025–2026 ในจำนวนนี้ 25 รายการมีช่องรหัสสินค้าและ 19 รายการมีลิงก์อ้างปี ตัวเลขนี้ใช้วัดความครบของช่องในแคตตาล็อกก่อนเริ่มทดลอง [แคตตาล็อกปัจจุบัน](../../data/rackets.js)

## ปัญหาที่ใช้ทดสอบ

แคตตาล็อกเก็บ `yearSrc`, `tensionSrc` และ `tensionByWeight` ส่วน `AUDIT` ในตัว build เก็บค่าที่ร้านแต่ละแห่งให้ไว้ ตัวนำเข้า Markdown เดิมเลือกลิงก์แรกเป็นแหล่งของทั้งแถว ตัดปีในวงเล็บท้ายชื่อ และย่อเพดานเอ็นเหลือค่าเดียวโดยเลือก 4U ก่อน [ตัวนำเข้า](../../scripts/merge_research.py) · [ตัว build แคตตาล็อก](../../scripts/build_rackets.py)

เคสสมมติ `Demo (2026)` ที่มี 3U สูงสุด 31 lbs และ 4U สูงสุด 30 lbs ใช้ทดสอบว่าตัวนำเข้ารุ่นใหม่รักษา ID และเพดานทั้งสองเวต พร้อมลิงก์ของแต่ละค่าครบหลัง build [เทสต์ตัวนำเข้า](../../tests/test_merge_research.py)

## วิธีเก็บหลักฐาน

1. ใช้หนึ่งแถวต่อหนึ่งค่าที่ต้องการยืนยัน ระบุ `racketId`, รหัสสินค้าตามแหล่ง, ชื่อตรงรุ่น, ตลาด, เวต, ช่องข้อมูล, ตัวเลขพร้อมหน่วย, URL, วันที่ตรวจ และหัวข้อหรือหน้า PDF ที่ตรวจได้ซ้ำ เก็บคำกำกับของแหล่งอย่าง `Stringing Advice` หรือ `String tension LBS` ด้วย เพื่อแยกช่วงแนะนำกับเพดานเมื่อแหล่งระบุความหมายไว้
2. เริ่มจากประกาศหรือแคตตาล็อกผู้ผลิตและหน้าสินค้าตัวแทนทางการ ใช้หน้าเปิดตัวสำหรับปี ใช้ตารางสเปกสำหรับเวตและเอ็น ร้านไทยใช้ยืนยันการวางขายในไทยและราคา ณ วันที่ตรวจ แหล่งรองใช้ตามหาแหล่งต้นทางหรือตรวจซ้ำเมื่อระบุรหัสเต็มและเวตชัด ตรวจด้วยว่าร้านสองแห่งคัดลอกจากตารางเดียวกันหรือเปล่า
3. กำหนดสถานะรายช่องเป็น `ยืนยันแล้ว`, `ประมาณ`, `แหล่งขัดกัน` หรือ `ยังไม่พบ` เมื่อค่าต่างกันให้ตรวจรหัส เวต ตลาด ฉบับของแคตตาล็อก และคำกำกับ ถ้าต่างกันตามตลาดให้บันทึกไว้ทั้งสองค่า ถ้ายังหาข้อสรุปไม่ได้ให้ระงับค่าที่หน้า Match จะนำไปใช้ และเก็บลิงก์พร้อมเหตุผลไว้ตรวจต่อ [เงื่อนไขหน้า Match](../../app.js#L1208)
4. เปิดหลักฐานทวนอีกครั้งก่อนนำเข้า โดยให้คนตรวจคนที่สองลองเทียบเคสชื่อคล้ายและเคสขัดกัน ใช้ผล `AUDIT` ช่วยหาแหล่งที่เคยจับคู่ แล้วให้เทสต์การค้นตามรหัสและเพดานตามเวตตรวจผลหลัง build [เทสต์แคตตาล็อก](../../tests/cases.js#L87)

## นำเข้าหลักฐาน

สร้างไฟล์ JSON เป็นอาร์เรย์ของรุ่นที่มี `racketId` อยู่ในแคตตาล็อก ใช้ `modelCode` ตรงกับรหัสที่มีอยู่และเลือกตลาดที่จะใช้กับเวตและเพดานเอ็นอย่างชัดเจน ตัวอย่างนี้ใช้หลักฐานสากลของ Yonex [สเปก Astrox 100VA Tour](https://www.yonex.com/badminton/racquets/astrox-100va-tour)

```json
[
  {
    "racketId": "yonex-astrox-100va-tour",
    "modelCode": "AX100VAT",
    "market": "GLOBAL",
    "evidence": [
      {
        "field": "tension",
        "market": "GLOBAL",
        "weight": "3U",
        "unit": "lbs",
        "value": [21, 29],
        "status": "confirmed",
        "sourceCode": "AX100VAT",
        "source": "https://www.yonex.com/badminton/racquets/astrox-100va-tour",
        "locator": "Specs → Stringing Advice → 3U",
        "checkedOn": "2026-11-24"
      },
      {
        "field": "tension",
        "market": "GLOBAL",
        "weight": "4U",
        "unit": "lbs",
        "value": [20, 28],
        "status": "confirmed",
        "sourceCode": "AX100VAT",
        "source": "https://www.yonex.com/badminton/racquets/astrox-100va-tour",
        "locator": "Specs → Stringing Advice → 4U",
        "checkedOn": "2026-11-24"
      }
    ]
  }
]
```

- `tension` ใช้ `[ต่ำสุด, สูงสุด]` หากแหล่งระบุเฉพาะเพดาน ให้ใช้ `[null, สูงสุด]` เก็บแต่ละเวตเป็นคนละรายการและตรวจรหัสย่อยตามต้นทาง
- `weights` เป็นรายการเวต เช่น `["3U", "4U"]` และ `modelCode` ใช้เติมรหัสที่ยังว่างเมื่อมีหลักฐานยืนยัน ตรวจว่าเป็นรุ่นในแคตตาล็อกก่อนนำเข้า รุ่นใหม่สร้าง ID ผ่านไฟล์ override ตามขั้นตอนปกติ
- `year` เป็นปีเปิดตัว ตัว build จะเผยแพร่ปีจากหลักฐานที่ระบุขอบเขต `GLOBAL` ส่วน `availableOn` เป็นวันที่เริ่มขายของแต่ละตลาดในรูปแบบ `YYYY-MM-DD` และเก็บไว้ในบันทึกหลักฐาน
- สถานะใช้ `confirmed`, `estimated`, `conflicting` หรือ `missing` สำหรับ `missing` เว้นค่าและลิงก์ได้ และเว้นเวตได้ถ้ายังยืนยันเวตไม่ได้ ถ้าแหล่งในตลาดที่เลือกให้ค่าเพดานต่างกัน ตัว build จะเก็บหลักฐานทั้งสองและพักเวตนั้นไว้

```bash
python3 scripts/merge_research.py research-batch.json
python3 scripts/merge_research.py research-batch.json --apply
python3 scripts/build_rackets.py
node tests/run.js
python3 -m unittest discover -s tests
```

คำสั่งแรกแสดงรายการก่อนเขียนจริง ส่วน `--apply` บันทึกที่ `data/racket-research.json` แล้วตัว build ใส่หลักฐานที่ใช้เผยแพร่ไว้ใน `researchEvidence` ของรุ่นนั้น โน้ต Markdown เดิมเปิดดูผ่านคำสั่งรูปแบบเดิมได้เพื่อคัดหลักฐานเข้ารูปแบบ JSON

## วัดผลหลังจบรอบ

- **ความครอบคลุม** นับจำนวนช่องที่ยืนยันได้ต่อช่องที่ตั้งใจตรวจ แยกตามแบรนด์และตลาด นับเพดานเอ็นตามจำนวนเวตที่ต้องตรวจ
- **ตรวจซ้ำได้** ทุกค่าที่เผยแพร่จากรอบนี้เปิดหลักฐานแล้วเจอรหัส เวต และตัวเลขตรงกัน บันทึกเหตุผลให้ครบทุกช่องที่ยังเปิดไว้
- **คุณภาพหลัง build** ตรวจว่าค้นรหัสได้ตรงรุ่น หน้า Match เห็นเพดานถูกเวต และค่าที่ยังขัดกันไม่กลายเป็นค่าที่ยืนยันแล้ว
- **ประหยัดเวลารอบถัดไป** จับเวลาเฉลี่ยในการหาหลักฐานและทวนหนึ่งรุ่น พร้อมนับช่องที่ต้องแก้หลังคนที่สองตรวจ ใช้ผลตัดสินว่าขั้นตอนไหนควรทำอัตโนมัติเพิ่ม
